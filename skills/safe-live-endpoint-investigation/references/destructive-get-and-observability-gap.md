*사례 요약: 부작용 있는 GET과 관측 공백*

*상황*

- 사용자는 dev 서비스의 특정 경로가 500을 반환한다고 보고했다.
- 인스턴스와 ALB 타깃은 모두 정상으로 표시됐다.
- Loki 로그와 CPU·메모리·디스크 시계열은 모두 빈 결과였다.
- IaC 저장소는 앱을 직접 포함하지 않고 별도 공개 앱 저장소의 release tag를 pin하고 있었다.

*코드에서 확인된 실제 동작*

문제 경로는 이름과 달리 단순 오류 재현용이 아니었다. 호출 한 번마다 다음 부작용이 있었다.

- DB 연결 20개를 열고 닫지 않음
- 약 8초간 CPU 소모
- ERROR 로그 기록
- 마지막에 HTTP 500 반환

여러 번 호출해 로드밸런서의 양쪽 백엔드를 확인하면 연결 누수가 호출 수만큼 누적된다. 4회 호출이라면 코드상 최대 80개 연결이 남을 수 있다. 실제 사례에서는 이후 health check는 200을 유지했지만 정상 루트는 DB 연결 불가를 표시했고 DB 의존 경로는 500이 됐다.

*왜 ALB는 계속 healthy였나*

health check 경로가 DB를 검사하지 않는 가벼운 liveness endpoint였다. 따라서 다음 두 문장은 동시에 참일 수 있다.

- ALB target: `healthy`
- 애플리케이션 DB 기능: 장애

RCA에서 liveness와 dependency readiness를 분리해야 한다.

*왜 로그가 없었나*

앱은 로컬 파일에 ERROR를 기록하도록 구현돼 있었지만, 중앙 로그와 node metrics가 모두 비어 있었다. 최근 교체된 fleet에서는 promtail/node_exporter 같은 monitoring agent가 아직 배포되지 않았을 수 있다. 빈 검색 결과는 “ERROR 없음”의 증거가 아니다.

*재사용 체크리스트*

- [ ] 사용자 보고만으로 충분한 재현 근거가 있는가?
- [ ] 경로명이나 문서가 장애 주입을 암시하는가?
- [ ] 배포 태그와 라우트 코드를 먼저 확인했는가?
- [ ] 요청이 DB 연결, CPU, 메모리, 파일, 큐, 외부 API에 영향을 주는가?
- [ ] health check가 실제 dependency를 검사하는가?
- [ ] 로그와 metrics가 모두 비어 있다면 agent 배포 상태를 의심했는가?
- [ ] 앱 코드 저장소와 IaC 저장소를 구분했는가?
- [ ] 직접 probe했다면 1회로 제한하고 이후 상태를 확인했는가?

*안전한 결론 예시*

`해당 500은 장애 주입 라우트의 설계된 동작이며, 호출 자체가 DB 연결을 누수시킵니다. 추가 재현은 중단했습니다. ALB health check는 DB를 검사하지 않아 healthy 상태가 실제 DB 기능 정상 여부를 보장하지 않습니다.`
