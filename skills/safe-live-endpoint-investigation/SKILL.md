*목적*

운영 또는 실습 환경의 HTTP 5xx를 조사할 때, 재현 요청 자체가 상태를 변경하거나 장애를 증폭할 수 있다는 전제에서 안전하게 원인을 좁힌다. 저장소별 운영 runbook이 있으면 그것을 먼저 따르며, 이 스킬은 안전한 HTTP 검증 원칙을 보완한다.

*핵심 원칙*

- `GET`이라는 이유만으로 안전하거나 멱등이라고 가정하지 않는다. `/troublemaker`, `/leak`, `/chaos`, `/debug`, `/load`, `/stress`처럼 장애 주입을 암시하는 경로는 특히 위험하다.
- 사용자가 이미 재현 사실과 응답 코드를 제공했다면, 먼저 리소스 상태·로그·메트릭·배포 버전·라우트 구현을 조회한다. 같은 요청을 반복해서 “확인”하지 않는다.
- 라이브 재현 전에는 가능하면 README, OpenAPI, 라우트 코드, 배포된 태그를 확인해 부작용을 판별한다.
- 부작용을 배제하지 못한 요청은 실행하지 않는다. 꼭 필요한 저위험 검증만 단 1회 수행하고, 반복·병렬·로드밸런서 백엔드 분산 확인 목적의 다회 호출을 금지한다.
- 진단 전용 권한이나 runbook에서는 재시작, PR, 배포, silence 등 변경을 실행하지 않는다. 권고와 근거만 보고한다.

*절차*

1. *범위와 권한 확인*
   - 환경, 서비스, 경로, 관찰된 상태 코드, 최초 관찰 시각을 정리한다.
   - 저장소별 incident runbook과 허용된 읽기/변경 경로를 확인한다.

2. *재현보다 먼저 읽기*
   - 인스턴스 상태와 ALB 타깃 상태를 조회한다.
   - 최근 5xx/ERROR 로그와 CPU·메모리·디스크 시계열을 조회한다.
   - 현재 배포 버전과 해당 라우트의 README/코드를 확인한다.
   - 앱 코드가 별도 저장소에 있고 IaC는 태그만 pin하는 구조인지 확인한다.

3. *라우트 위험도 판정*
   - DB 연결 누수, CPU burn, 메모리 ballast, 파일 쓰기, 큐 적재, 외부 API 호출, 데이터 변경, 프로세스 종료가 있으면 장애 주입 경로로 분류한다.
   - 장애 주입 경로는 라이브에서 호출하지 않고 코드와 기존 관측으로 판정한다.

4. *안전한 검증*
   - `/healthz`와 정상 비즈니스 경로를 구분한다. health check가 DB 같은 의존성을 검사하지 않으면 ALB `healthy`만으로 서비스 정상이라고 결론내리지 않는다.
   - 필요할 때만 정상 경로를 1회 조회해 dependency 상태를 확인한다.
   - 요청 직후 상태가 악화되면 즉시 추가 호출을 중단하고, 요청이 만든 부작용 가능성을 보고에 명시한다.

5. *관측 공백 해석*
   - 로그와 모든 시스템 메트릭이 함께 비어 있고 fleet이 최근 교체됐다면, “오류 없음”이 아니라 monitoring agent 미배포/no-data 가능성을 우선 검토한다.
   - 관측 공백과 서비스 정상 여부를 분리해 보고한다.

6. *수정 경로 결정*
   - 실제 앱 코드 저장소와 PR 생성 권한을 확인한다. IaC 저장소에서 앱 버전 태그만 지정하는 경우 앱 수정 PR을 IaC 변경으로 대체하지 않는다.
   - 변경 권한이 없으면 PR을 만들었다고 암시하지 말고, 대상 저장소·권고 변경·필요한 복구 조치를 정확히 적는다.

*보고 형식*

- 첫 줄: 원인 판정과 현재 영향.
- 이어서: 리소스 상태, 정상 경로, 로그/메트릭, 코드 근거, 관측 한계.
- 마지막: 즉시 복구 권고와 영구 수정 권고를 분리한다.
- 직접 실행한 probe가 상태를 바꿨을 가능성이 있으면 호출 횟수와 예상 부작용을 숨기지 않는다.

*금지 사항*

- 장애 주입 가능성이 있는 경로를 여러 번 호출해 백엔드별 동작을 확인하는 행위.
- 빈 로그 결과를 “에러 없음”으로 해석하는 행위.
- ALB health check 성공만으로 DB·큐·외부 API까지 정상이라고 단정하는 행위.
- 앱 코드 저장소를 확인하지 않고 인프라 PR을 앱 수정으로 제시하는 행위.
